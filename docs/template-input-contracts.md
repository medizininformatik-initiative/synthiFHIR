# Workbook input fields

Use the supplied workbook's sheet names, column headings and dropdowns. This page
summarizes how input fields map to FHIR. Detailed instructions are available for
[diagnoses](diagnosis-workbook.md), [contacts](synthea-movements.md) and
[selection lists](clinical-selections.md).

## Person and address

`Person` records identity, consent and address fields. `Vorname`, `Nachname` and
`Geburtsdatum` offer missing-reason suggestions and allow freely typed input.
Empty cells omit the corresponding FHIR value. Choose an explicit label such as
`Unbekannt (Data Absent Reason)` or enter `!dar:unknown` to emit a missing reason.
In name fields, ordinary words such as `Unbekannt` remain literal names. Given
names separated by spaces become individual FHIR given-name entries. Birth dates
accept a full date or reduced precision such as `1980` or `1980-05`.

Enter address components
in `Straße`, `Postleitzahl`, `Ort`, `Bundesland` and `Land`. Available components
are preserved when the country is empty. An entirely empty address is omitted.
Address components accept explicit `!dar:` markers or suffixed missing-reason labels.
An empty gender is omitted; an explicitly entered `unknown` remains a gender code.
For country `DE`, German state names become
ISO 3166-2 codes.

See [identifier rules](#identifiers) for patient numbers.

## Identifiers

Resource identifiers are generated by configured identifier rules. Select the
resource types, such as `Patient`, `Condition`, `Medication` or `Observation`,
and supply the system, value pattern and optional use or type coding.
Without a matching enabled rule, the corresponding `identifier` is omitted.
Technical resource IDs and references remain available independently.

For observations, use `Observation` to target both observation sheets, or
`Observation.laboratory` and `Observation.vitalSigns` for explicit matching
categories. A pattern such as `{resourceId}` copies the technical ID into the
configured identifier. Type codings such as `MR` or `OBI` are optional; an
assigner is not automatically added.

In reference-only output, enabling the description includes an identifier in
the reference. The technical target ID is used when no target identifier is
available.

## Medication

`Medikation` separates product identity, ATC classification, ingredients and dose:

- `Präparatbezeichnung`, `Präparatcode` and `Präparatcodesystem` identify the product.
- `ATC-Code` provides the classification. `ATC-Version` accepts edition text, a
  readable DAR selection or an empty cell for omission; see [version handling](terminology-versions.md).
  A version without an ATC code is retained in a coding with system and version.
- `Wirkstoffcode` and `Wirkstoffcodesystem` identify ingredients. Separate multiple
  ingredients with semicolons; all use the selected system. Supported systems are
  ASK, UNII, SNOMED CT and RxNorm. Each ingredient becomes a separate FHIR entry.
- `Darreichungsform` is the dose-form text. `Einzeldosis` is the amount per dose.

| Medication type | `Dokumentationszeitpunkt` | `Beginn` / `Ende` |
| --- | --- | --- |
| `Verordnung` (request) | Optional `authoredOn` | Leave empty. |
| `Verabreichung` (administration) | Leave empty. | `effectiveDateTime` or `effectivePeriod`; empty values are omitted. |
| `Medikationsaussage` (statement) | Optional `dateAsserted` | `effectiveDateTime` or `effectivePeriod`; empty values are omitted. |

Empty times and ingredients are omitted. Use an explicit Data Absent Reason to
represent why a value is unavailable.
Codes and systems can be entered independently. Status choices depend on the
medication type. Empty status and request intent fields are omitted.

All medication types retain supplied dose fields as a structured quantity,
independently of dosage text and daily frequency. `Dosiereinheitcodesystem`
suggests `http://unitsofmeasure.org` and accepts arbitrary system text without
translating names. Empty system, unit and value fields are omitted; missing reasons
are emitted only when explicitly supplied. `Dosiereinheit` is copied to code and
unit as entered, without UCUM normalization.
For requests and statements, an integer daily frequency produces structured
timing independently of the dose. Other frequencies remain in dosage text.
Supplied dosage text is retained alongside the structured fields; textual
fallbacks also retain partial instructions. Administrations retain daily frequency
as text.
Profile requirements, code validity
and clinical plausibility are left to optional FHIR validation.

Medication IDs include product details, ATC version, form and ingredient system;
references use those generated IDs.

## Observations

See [identifier rules](#identifiers) for observation identifiers.

The investigation code identifies what was measured. An additional coding describes
the same investigation. Result code/system describe a coded answer.
`Einheit`, `Einheitencode` and `Einheitencodesystem` map independently to the
quantity's unit label, code and system. The system dropdown suggests
`http://unitsofmeasure.org` and accepts arbitrary text. Supplied values are emitted
unchanged; empty fields are omitted without inferred codes, systems or missing
reasons. Numeric comparisons such as `<5`, `<=5`, `>5` and `>=5` are supported
with or without a unit code or system, including component rows. A quantity with
unit information but no numeric value preserves the supplied unit fields.
The optional FHIR validator can report combinations such as a code without a system.

Laboratory and clinical documentation rows support number, text, coded answer,
Boolean values, components and missing values. Components follow their
parent row and refer to its `Untersuchung ID` through `Komponente von`.
A parent and its components form one Observation. Diagnostic reports use those
investigation IDs for result references.

Text results use `valueString` on both observation sheets. Empty status, category
and code-system fields are omitted. An entered category produces its corresponding
observation-category coding.
Laboratory-specific options apply to the explicit `laboratory` category, and
vital-sign options to `vital-signs`, both in the HL7 observation-category system.
The **Other Observations** group includes all remaining Observations, such as
surveys, social history and entries without a category. It is enabled by default.
These Observations retain their input contact reference and measurement values,
subject to general output rules. To output only patients, select Patient and
disable all other resource groups, including all three Observation groups.

## Other clinical fields

- `Prozedur`: procedure code/system, optional additional coding, performed start/end,
  status and category. Empty codesystem, version and category cells are omitted.
  Contact periods and procedure periods are separate inputs.
- `DocumentReference`: see [Document blocks](#document-blocks) for repeated codings,
  NLP processing status and embedded content or file references.
- `Impfung` and `Befundbericht`: event code/system, time and
  resource-specific status fields. See the workbook's field help.

## Document blocks

The `DocumentReference` sheet and CSV table require a `Dokument-ID` column.
An explicit ID starts one document. Following rows with an empty ID append
independent type codings and NLP status codes to that document. IDs must be unique
within the table. Empty rows and help-only rows are ignored. A continuation needs
a preceding valid document start.

Enter `Patient-ID`, optional `Fall-Nr`, `Dateipfad`, `Embed`, `Dokumenttext`,
`Status` and `Ausgabezeitpunkt` on the start row only. Each document start supplies
its own patient reference. The document key groups input rows; output FHIR IDs
follow the configured document ID sequence. Document type, date and status are
supplied explicitly.

Each row may supply one `Dokumentcode`, `Dokumentcodesystem` and
`Dokumentbezeichner`, and one `NLPStatus`. Type codings and NLP codes are collected
independently: sharing an input row does not relate them to each other. A document
label accompanying a coding becomes its `display`; a label without a coding is
retained in `type.text`. Multiple free labels are joined with line breaks.

| Dokument-ID | Patient-ID | Embed | Dokumenttext | Dokumentcode | Dokumentcodesystem | NLPStatus |
| --- | --- | --- | --- | --- | --- | --- |
| document-1 | patient-1 | Ja | Synthetic clinical text | AD010110 | http://dvmd.de/fhir/CodeSystem/kdl | preprocessed |
| | | | | BERI | http://ihe-d.de/CodeSystems/IHEXDStypeCode | format-change |
| | | | | | | surrogated |

`Embed` controls content for the whole document:

- `Ja` (case-insensitive): embed `Dokumenttext` as UTF-8 text. When text is empty,
  read and embed the file at `Dateipfad`. A text or path is required.
- `Nein` or empty: require `Dateipfad` and output its file URL. The converter does
  not read the file or embed a supplied `Dokumenttext`. File size and creation
  time are omitted in this mode. The receiver needs access to the referenced file.

Paths are resolved in the converter's filesystem, including its container when
running in Docker. The bundled `input/document-example.txt` supplies an embedded
file example. The starter workbook also includes inline text and URL-only examples.

NLP codes become separate `coding` entries in one extension's
`valueCodeableConcept`. The converter sets the fixed canonical identifiers:

- Extension: `https://www.medizininformatik-initiative.de/fhir/ext/modul-dokument/StructureDefinition/mii-ex-dokument-nlp-processing-status`
- Coding system: `https://www.medizininformatik-initiative.de/fhir/ext/modul-dokument/CodeSystem/mii-cs-dokument-nlp-processing-status`

With no NLP code, the extension is absent. The `Codes` sheet suggests individual
codes and common document type codes/systems, while allowing free input.
`format-change` and `content-change` require `preprocessed`; `preanno`, `deid`
and `semantic` require `annotated`. Unknown codes and missing parent codes are
listed in the import report's `documentIssues`, without changing or excluding
explicit values. Processing status describes supplied content; it does not perform
NLP processing or de-identification. `annotated` with `deid` describes annotations;
`surrogated` describes replacement of selected information.

The terminology follows the [MII NLP processing status definition and examples](https://simplifier.net/guide/medizininformatikinitiative-dokument/MIIIGModulDokument/TechnischeImplementierung/FHIRProfile/NLP-Processing-Status-Extension.page.md?version=preview)
(version 2027.0.0-ballot.2). Adding this extension does not by itself establish
conformance to the complete MII DocumentReference profile.

## General treatment plans

`Behandlungsplan` represents a general FHIR CarePlan. A row with `Patient-ID`
starts a new plan, including when the patient and `Fall-Nr` repeat. A following
row with both identifiers empty adds an activity to that plan. Empty rows are
ignored. The first row can include the first activity; a plan can also have no
activities. Continuations require a preceding plan and cannot contain plan fields.

The first row supplies `Titel`, `Beschreibung`, `Planstatus`, `Absicht`,
`Erstellungsdatum`, `Beginn`, `Ende` and one category (`Kategorietext`,
`Kategoriecode`, `Kategoriecodesystem`, `Kategorieversion`). Creation and validity
period are independent. An empty `Fall-Nr` leaves the plan without an encounter.

Each activity has `Aktivitätstext`, `Aktivitätscode`, `Aktivitätscodesystem`,
`Aktivitätsversion`, `Aktivitätsstatus`, `Aktivitätsstatusgrund`,
`Aktivitätsbeginn`, `Aktivitätsende` and `Aktivitätsort`. Text and coding form
`activity.detail.code`; the reason is `statusReason.text`, dates form
`scheduledPeriod`, and the location is a display text. Activity fields are never
inherited from another row. Dropdowns offer suggestions and allow other values;
code systems accept URI values. Empty properties stay absent.

Technical plan IDs are generated from the patient and input row. The sheet does
not assert conformance to specialist CarePlan profiles. See
[Synthea import](synthea-clinical-import.md) for mapped fields and reported losses.

## Missing values

An empty clinical field omits the corresponding property, including fields required
by a FHIR profile. Conversion does not fill gaps to satisfy validation. Explicit missing-value
choices such as `Unbekannt (Data Absent Reason)` or `!dar:unknown` create the
appropriate FHIR extension. [Selection lists](clinical-selections.md) describe
where those choices apply. Profile requirements are checked by the optional
[FHIR validator](fhir-validation.md).

In CSV input, an omitted optional `Fall-Nr` column leaves the explicit encounter
association absent, just like an empty cell. Configured encounter assignment rules
still apply.
